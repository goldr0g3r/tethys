## 1. Scope

The SCMP describes how Tethys identifies, versions, baselines,
releases, and audits its software configuration items.

Satisfies:

- ECSS-Q-ST-80C §6 (software configuration management).
- IEEE 828-2012 (Standard for Configuration Management in Systems and
  Software Engineering, informational).
- NPR 7150.2D §3.5 (software configuration management).

## 3. Repository discipline (parent §6.1)

- **Mono-repo** at https://github.com/goldr0g3r/tethys.
- **Branch model**: trunk-based (short feature branches off `main`),
  squash-merge. Release branches only at v1.0+.
- **Branch protection** on `main`: required reviews, required status
  checks, linear history, signed commits.
  Source: [`infrastructure/github/branch-protection.json`](../infrastructure/github/branch-protection.json).
- **Conventional Commits** for every commit subject + every PR title.
  Source: [`.cursor/rules/conventional-commits.mdc`](../.cursor/rules/conventional-commits.mdc).
- **Tags == releases**. Tags `vX.Y.Z` trigger [`release.yml`](../.github/workflows/release.yml).

## 4. Versioning

SemVer for both `tethys-master` and `tethys-slave`. CHANGELOG generated
on every tag by semantic-release. Pre-1.0 grace: MINOR may break.

## 5. Baselines

| Baseline | Trigger | Artefacts |
| --- | --- | --- |
| Phase-Acceptance | Each Phase-Acceptance Issue closes | Phase research note + demo recording + traceability rows |
| v0.x.y | Tag push | PyInstaller bundles + slave tarball + Docker image + SBOM + GitHub Release |
| v1.0 | Phase 11 completion | All of the above + case-study PDF + Sphinx site |

## 6. Change control

1. Issue opened with appropriate labels (`type/*`, `phase/*`, `area/*`,
   `prio/*`).
2. Sub-plan drafted under `.cursor/plans/<id>_<topic>.plan.md`.
3. Draft PR opened off `main`.
4. CI runs; human + Copilot review.
5. Squash-merge with the Conventional Commit title.
6. Status sync (parent §6.8).

ADR-level changes (architecture, profiles, transports, license, key
toolchain) require an ADR in `proposed` -> `accepted` flow before code
lands.

## 7. Supply chain (parent §6.7 + runbook)

- **Dependencies**: every Python wheel / CMake `FetchContent_Declare`
  / GitHub Action pinned exactly per
  [`.cursor/rules/version-pinning.mdc`](../.cursor/rules/version-pinning.mdc).
- **Renovate / Dependabot**: proposes upgrades via PR.
- **SBOM**: CycloneDX, generated by [`sbom.yml`](../.github/workflows/sbom.yml)
  on every tag.
- **CVE triage**: `pip-audit` + `osv-scanner` per
  [`docs/runbooks/supply-chain-and-sbom.md`](runbooks/supply-chain-and-sbom.md).

## 8. Records + retention

Source of record is GitHub:

- Issues + PRs are permanent (never force-delete on `main`).
- Branch protection forbids force-pushes on `main`.
- Tags are immutable.
- Releases attach the SBOM + checksums + artefacts.

Phase-acceptance records: research note + closed Issue + PR list + demo
recording (linked from the Release).

## 9. Audit

- **Pre-release audit**: `docs/runbooks/release-process.md` §2

- **Quarterly runbook audit**: `docs/runbooks/README.md` §How runbooks

- **Per-PR audit**: GitHub branch protection (required reviewers,
