# Runbook - Supply chain and SBOM

> Audience: an engineer maintaining dependencies, reviewing Renovate /
> Dependabot PRs, generating CycloneDX SBOMs, rotating PATs, or triaging a
> dependency CVE.
> Goal: from "Renovate just opened 5 PRs" or "PyPI just published a security
> advisory" to "dependencies up to date, CI green, SBOM regenerated". Wall-
> clock target: **20 minutes per dependency batch**, **<1 hour for CVE
> triage**.
> Style: numbered sections, both shells, expected outputs.
>
> Implements parent plan §5 (free-tool-only) + §6.7 (`dependency-review.yml`,
> `sbom.yml`) + section 6.6 (PAT rotation cadence).

## 1. Inventory

Tethys has four dependency surfaces, each with its own lockfile / pin format:

| Surface | Lockfile | Manager | SBOM tool |
| --- | --- | --- | --- |
| `master/` Python deps | `master/uv.lock` | `uv` | `cyclonedx-py` (from `cyclonedx-bom` package) |
| `simulator/` Python deps | `simulator/uv.lock` | `uv` | `cyclonedx-py` |
| `slave/` C deps (Unity, libFuzzer, etc.) | `slave/CMakeLists.txt` `FetchContent_Declare` SHA pins | CMake | `cyclonedx-cli` against the build's compile_commands.json |
| GitHub Actions | `.github/workflows/*.yml` (SHA pins) | Renovate / Dependabot | enumerated in `sbom.yml` workflow |

The CycloneDX top-level SBOM is the union of all four, generated by
`.github/workflows/sbom.yml` on every release tag.

## 2. Generating a CycloneDX SBOM

### 2.1 Locally

```powershell
cd master
uvx cyclonedx-py environment . --output-file ../sbom-master.json
cd ../simulator
uvx cyclonedx-py environment . --output-file ../sbom-simulator.json
cd ..
# Slave SBOM requires the build's compile_commands.json
docker run --rm -v ${PWD}:/work cyclonedx/cyclonedx-cli \
  add files --input-file /work/slave/build/compile_commands.json `
  --output-file /work/sbom-slave.json
# Merge
docker run --rm -v ${PWD}:/work cyclonedx/cyclonedx-cli \
  merge --input-files sbom-master.json sbom-simulator.json sbom-slave.json `
  --output-file sbom-tethys.json
```

```bash
cd master
uvx cyclonedx-py environment . --output-file ../sbom-master.json
cd ../simulator
uvx cyclonedx-py environment . --output-file ../sbom-simulator.json
cd ..
docker run --rm -v "$PWD:/work" cyclonedx/cyclonedx-cli \
  add files --input-file /work/slave/build/compile_commands.json \
  --output-file /work/sbom-slave.json
docker run --rm -v "$PWD:/work" cyclonedx/cyclonedx-cli \
  merge --input-files sbom-master.json sbom-simulator.json sbom-slave.json \
  --output-file sbom-tethys.json
```

Expected output: `sbom-tethys.json` ~50-200 KB depending on phase.

### 2.2 In CI

`.github/workflows/sbom.yml` triggers on `push: tags: ['v*']` and runs the
above sequence in a clean Ubuntu container. The resulting SBOM is attached to
the GitHub Release as `tethys-sbom-vX.Y.Z.cyclonedx.json`.

### 2.3 Validate

```bash
docker run --rm -i cyclonedx/cyclonedx-cli validate \
  --input-format json --input-version v1_5 \
  --input-file - < sbom-tethys.json
```

Expected: `BOM is valid`.

## 3. Reviewing Renovate / Dependabot PRs

Tethys ships both Renovate (`.github/renovate.json`) and Dependabot
(`.github/dependabot.yml`). Both auto-open PRs when dependencies have updates.

### 3.1 Triage cadence

- **Weekly:** review the queue every Monday.
- **Out-of-cycle:** any PR labelled `security` (CVE) is reviewed within 24 h.

```powershell
gh pr list --label "dependencies" --json number,title,labels,createdAt --jq '
  .[] | "\(.number)\t\(.createdAt | split("T")[0])\t\(.title)"'
```

```bash
gh pr list --label "dependencies" --json number,title,labels,createdAt --jq '
  .[] | "\(.number)\t\(.createdAt | split("T")[0])\t\(.title)"'
```

### 3.2 Per-PR check

For each:

1. **CI green?** All required-status-check passes.
2. **Changelog skim:** any breaking changes? `gh pr view <N> --json body
   --jq .body` then read the upstream release notes link.
3. **License unchanged?** `dependency-review.yml` workflow output.
4. **CVE backport?** look for the CVE number in the PR title/body; if yes,
   prioritise.
5. **MISRA gate clean?** for slave/-touching deps - the gate runs as part of
   CI.
6. **Test impact:** does the upgrade change behaviour the regression suite
   covers? Run targeted tests locally if uncertain.

### 3.3 Approve + merge

```powershell
gh pr review <N> --approve --body "LGTM. CVE check + changelog skim done."
gh pr merge <N> --squash --delete-branch
```

```bash
gh pr review <N> --approve --body "LGTM. CVE check + changelog skim done."
gh pr merge <N> --squash --delete-branch
```

### 3.4 Group updates

For minor / patch bumps Renovate is configured to group them per package
ecosystem (e.g. all GitHub Actions in one PR per week). Review the grouped PR
once; merge if green.

### 3.5 Holdback

If an upgrade is blocked (upstream regression, breaking API change without
mitigation):

- Comment on the PR explaining the block.
- Add the package to the Renovate ignore list (`packageRules`) with a TODO
  date.
- Close the PR.

## 4. CVE triage workflow

### 4.1 Discover

CVEs land in the queue via:

- **GitHub Dependabot Alerts** (private; visible to maintainers under the
  Security tab).
- **pip-audit** running on every PR (`dependency-review.yml`) + nightly.
- **osv-scanner** running on every PR + nightly.
- **External report** (a user opens an issue / advisory).

### 4.2 Confirm

```powershell
uvx pip-audit -r master/pyproject.toml --format=json
uvx pip-audit -r simulator/pyproject.toml --format=json
docker run --rm -v ${PWD}:/work ghcr.io/google/osv-scanner:latest --lockfile=/work/master/uv.lock
```

```bash
uvx pip-audit -r master/pyproject.toml --format=json
uvx pip-audit -r simulator/pyproject.toml --format=json
docker run --rm -v "$PWD:/work" ghcr.io/google/osv-scanner:latest --lockfile=/work/master/uv.lock
```

Expected: list of affected packages with CVE id + severity + fixed-in version.

### 4.3 Triage

For each CVE:

- **Exploitable in our usage?** Read the CVE description; check whether
  Tethys exercises the affected code path.
- **Severity?** Use CVSS score; pair with our severity matrix
  ([`incident-and-defect.md`](incident-and-defect.md) §1).
- **Fix available?** If a patched version exists, file a Renovate-style PR
  manually:

  ```bash
  cd master && uv lock --upgrade-package <package>
  git checkout -b fix/cve-<id>-<package>
  git add master/uv.lock master/pyproject.toml
  git commit -m "fix(deps): bump <package> to <ver> for CVE-<id>"
  git push -u origin HEAD
  gh pr create --title "fix(deps): bump <package> to <ver> for CVE-<id>" --body "Closes the <CVE> vulnerability."
  ```

- **No fix yet?** Open an issue with `security` + `prio/p0` + `blocked`
  labels; pin to the workaround if any.

### 4.4 Document

Add a row to `docs/incidents/<YYYY-MM-DD>-cve-<id>.md` per
[`incident-and-defect.md`](incident-and-defect.md) §5 if severity is Critical.

## 5. PAT rotation

Per parent §6.6, fine-grained PATs are rotated every **90 days**. The
`tethys-bootstrap-<YYYY-MM>` PAT created during `github-setup.md` is the
authoritative reference.

### 5.1 Calendar

| PAT name | Owner | Last rotated | Next rotation |
| --- | --- | --- | --- |
| `tethys-bootstrap-2026-05` | @goldr0g3r | 2026-05-14 | 2026-08-12 |
| `tethys-actions-bot` | @goldr0g3r | 2026-05-14 | 2026-08-12 |

Maintain the table; one row per PAT.

### 5.2 Rotation procedure

1. Create the new PAT at <https://github.com/settings/tokens?type=beta>
   matching the previous scope set (see `github-setup.md` §2).
2. Update every consumer (CI secret, local `.gh/config.yml`, etc.).

   ```powershell
   gh secret set GH_PAT --body $env:NEW_PAT --repo goldr0g3r/tethys
   ```

   ```bash
   echo "$NEW_PAT" | gh secret set GH_PAT --repo goldr0g3r/tethys
   ```

3. Smoke test:

   ```bash
   gh api user --jq .login
   ```

   Expected: your username.

4. Revoke the old PAT at <https://github.com/settings/tokens>.
5. Update the calendar row above.

## 6. License audit

`dependency-review.yml` checks every PR against the allow-list:

```yaml
allow-licenses: MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC,
  LGPL-2.1, LGPL-2.1-only, LGPL-2.1-or-later, LGPL-3.0, LGPL-3.0-only,
  LGPL-3.0-or-later, MPL-2.0, GPL-2.0, GPL-2.0-only, GPL-2.0-or-later,
  GPL-3.0, GPL-3.0-only, GPL-3.0-or-later, Unlicense, CC0-1.0, Zlib,
  BlueOak-1.0.0, Python-2.0, PSF-2.0
```

Per [`free-tool-only.mdc`](../../.cursor/rules/free-tool-only.mdc), any
non-allow-listed license requires explicit ADR approval before the dep can
merge.

### 6.1 Manual license audit

Quarterly:

```bash
uvx pip-licenses --from=meta --format=markdown --output-file=docs/licenses-python.md
```

For C deps, the SBOM `licenses` field has the same info; extract via
`cyclonedx-cli query`.

## 7. Adding a new dependency

Per [`free-tool-only.mdc`](../../.cursor/rules/free-tool-only.mdc) the PR
opening must include:

```text
Tool: <name>
License: <SPDX identifier>
Free for: <commercial / non-commercial / personal>
Replaces: <existing free tool>, or "new capability"
ADR: <link to ADR if architectural>
```

Steps:

1. Audit the license against the allow-list.
2. Audit upstream activity (last release < 12 months; > 100 GitHub stars
   ideal but not mandatory).
3. Audit transitive deps (`pip-licenses --packages <package>`).
4. Pin to exact version in lockfile (per `version-pinning.mdc`).
5. Run `pip-audit` / `osv-scanner` to confirm no known CVEs.
6. Open PR per the standard flow; PR-title gate validates Conventional
   Commits format.
