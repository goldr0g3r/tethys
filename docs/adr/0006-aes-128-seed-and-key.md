## Context and Problem Statement

The XCP 1.4 spec (S1 in [`phase-0-standards-matrix.csv`](../research/phase-0-standards-matrix.csv)) defines a generic seed-and-key authentication for protected commands. The specific cipher and key size are deployment choices. The space profile per [ADR-0001](0001-xcp-as-development-protocol.md) ([`space-profile-invariants.mdc`](../../.cursor/rules/space-profile-invariants.mdc)) requires authenticated service-mode unlock - without it an attacker on the flight bus could read calibration data or trigger STIM.

What cipher, key size, and key-derivation scheme should Tethys mandate for the space profile?

## Decision Drivers

- Cryptographic strength must match the threat model: an attacker with bus access trying to elevate from quiescent to service mode.
- Key material must not be stored in plaintext on the slave (firmware extraction is a credible attack on flight hardware).
- Slave runs on resource-constrained MCUs (STM32H7 at the top end); the implementation must fit comfortably with no dynamic allocation per [ADR-0005](0005-no-dynamic-allocation.md).
- The free-tool constraint per [ADR-0008](0008-license-free-toolchain.md) means we use a widely-vetted public reference (NIST FIPS-197 AES); no proprietary cipher.
- ECSS-E-ST-40C Rev.1 (S18) accepts AES as a recognised symmetric primitive.

## Considered Options

1. **No seed-and-key** (XCP open in service mode). Trivial; insecure.
2. **Custom 4-byte challenge/response** (e.g. CRC-32 of the seed). Cheap; very weak against a determined attacker.
3. **AES-128 derived 16-byte challenge/response per NIST FIPS-197.** Symmetric cipher; per-target key burned in at manufacturing time; single AES block over the seed produces the response.
4. **AES-256 derived 32-byte challenge/response.** Same scheme as Option 3 with a larger key + larger CTO payload.
5. **Asymmetric (e.g. ECDSA P-256 signature).** Higher security; significant code-size + RAM overhead; key-management complexity.

## Decision Outcome

Chose **Option 3** (AES-128 derived 16-byte challenge/response).

### Scheme

1. **Per-target key:** a 16-byte key burned into the slave at manufacturing time (stored in a write-once region; not readable via XCP). For the academic STM32H7 dev kit, the key sits in a fixed flash sector marked read-protected.
2. **Challenge (master → slave):** XCP `GET_SEED` returns a fresh 16-byte random seed generated by the slave (hardware RNG where available; pseudo-random fallback documented).
3. **Response (master computes):** `response = AES-128-encrypt(seed, key)` - one AES block, no chaining.
4. **Verification (slave):** `slave_response = AES-128-encrypt(seed_just_sent, local_key)`; compare; constant-time compare to prevent timing oracle.
5. **Outcome:** match → unlock service mode for 60 s inactivity timeout; mismatch → increment failure counter; 3 failures in 10 min → 10-min lockout; all attempts logged.

### Marine profile

The marine profile per [`marine-profile-invariants.mdc`](../../.cursor/rules/marine-profile-invariants.mdc) treats seed-and-key as **optional**. When enabled, marine deployments may use a custom 4-byte scheme (legacy hardware) or AES-128 (recommended). The ADR-0006 mechanism is reused; only the key size and challenge length differ.

## Consequences

- **Positive:** Industry-standard cipher; widely vetted; FIPS-197 conformance reads cleanly to certification reviewers.
- **Positive:** Constant-time AES-128 block fits comfortably in the slave footprint (canonical implementations are < 4 KB code, no RAM allocation beyond a 176-byte key schedule).
- **Positive:** Per-target key means compromise of one device does not compromise the fleet.
- **Negative:** Key-management process (per-target key burn) is operational complexity. Documented in `docs/runbooks/hardware-setup-stm32.md` (PR-6 forthcoming).
- **Negative:** AES-128 is breakable with sufficient cipher-text under known-plaintext attack; mitigated by infrequent unlock attempts (max 3 per 10 minutes) and short seed lifetime (one seed per unlock attempt).
- **Risk:** Hardware RNG on STM32H7 has known biases; pseudo-random fallback is software-only. **Mitigation:** Phase 8 security research note characterises the RNG and decides whether to mix in a counter or external entropy source. If software-only PRNG is the chosen path, it is reseeded from device-unique data at every boot.
- **Risk:** Side-channel attacks (DPA / SPA) on AES key extraction are not addressed by this ADR. **Mitigation:** out-of-scope for academic dev kit; documented for any future flight-hardware deployment.
